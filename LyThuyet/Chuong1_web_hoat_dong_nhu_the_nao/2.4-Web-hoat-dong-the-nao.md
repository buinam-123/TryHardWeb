## 0. Bức tranh tổng thể

Khi bạn gõ `https://shopee.vn/search?keyword=tai+nghe` rồi Enter, đại khái có chuỗi sự kiện sau:

```
 Bạn (trình duyệt)                                         Máy chủ Shopee
 ─────────────────                                         ──────────────
 1. Phân tích URL: scheme=https, domain=shopee.vn, path=/search, query=keyword=tai+nghe
 2. Hỏi DNS: "shopee.vn ở IP nào?"  ──►  DNS trả lời: 203.x.x.x
 3. Mở kết nối TCP tới 203.x.x.x cổng 443  ─────────────────────►
 4. Bắt tay TLS (thống nhất khóa mã hóa)  ◄──────────────────────►
 5. Gửi HTTP Request (đã mã hóa):
      GET /search?keyword=tai+nghe HTTP/1.1
      Host: shopee.vn
      Cookie: SPC_EC=...                  ─────────────────────►
                                                          6. Server xử lý: đọc cookie biết bạn là ai,
                                                             truy vấn database tìm "tai nghe"
 7. Nhận HTTP Response:                   ◄─────────────────────
      HTTP/1.1 200 OK
      Content-Type: text/html
      <html>...</html>
 8. Trình duyệt đọc HTML, thấy cần thêm CSS, JS, ảnh → lặp lại bước 5–7 cho từng file
 9. JS chạy, gọi thêm API (fetch) lấy dữ liệu JSON → vẽ danh sách sản phẩm lên màn hình
```

Mọi khái niệm trong mục này là **một mảnh** của chuỗi trên:

| Khái niệm | Nằm ở bước nào |
|---|---|
| Client – Server, Request – Response | Toàn bộ mô hình |
| URL | Bước 1 |
| DNS, IP, Domain | Bước 2–3 |
| Hosting | "Máy chủ" ở bên phải là gì, đặt ở đâu |
| HTTP | Bước 5, 7 |
| HTTPS / TLS | Bước 4 |
| Cookie / Session | Bước 5–6 (server nhận ra bạn) |
| Local Storage | Bước 9 (JS lưu dữ liệu trên máy bạn) |
| JSON, REST API | Bước 9 |
| Postman | Công cụ để bạn **tự đóng vai trình duyệt** gửi bước 5 và xem bước 7 |

Giữ bảng này trong đầu khi đọc tiếp.

## 1. Client – Server, Request – Response

### 1.1. Vấn đề cần giải quyết

Dữ liệu của Facebook (bài viết, ảnh, tin nhắn của hàng tỷ người) **không thể** nằm trên máy của từng người dùng. Nó phải nằm ở **một chỗ chung**, và mọi người **xin** dữ liệu từ chỗ đó khi cần.

→ Từ đó sinh ra mô hình hai vai:

- **Server (máy chủ)**: chương trình **chờ** và **phục vụ**. Nó giữ dữ liệu, chứa logic nghiệp vụ (kiểm tra mật khẩu, tính tiền giỏ hàng...).
- **Client (máy khách)**: chương trình **chủ động hỏi**. Trình duyệt, app điện thoại, Postman, một đoạn script Python... đều là client.

### 1.2. Điểm bản chất cần nhớ

1. **Client luôn là bên mở lời.** Server không tự nhiên "gửi" gì cho bạn nếu bạn không hỏi trước (trong HTTP thuần). Đây là lý do các web chat ngày xưa phải "hỏi liên tục mỗi 2 giây" (polling), và sau này mới có WebSocket / Server-Sent Events để giữ kết nối mở.
2. **"Server" là vai trò, không phải loại máy.** Laptop của bạn chạy `npm run dev` hay Spring Boot ở cổng 8080 → laptop đó **đang là server**. Trình duyệt trên chính laptop đó gọi `localhost:8080` → nó là client. Một máy có thể vừa là client vừa là server.
3. **Một server phục vụ rất nhiều client cùng lúc**, và một trang web thường do **nhiều server** phối hợp (server web, server database, server lưu ảnh, CDN...). Server này cũng có thể là client của server khác (backend của bạn gọi API thanh toán VNPay → backend đang là client của VNPay).

### 1.3. Request – Response: một lượt hỏi – đáp

Mỗi lần giao tiếp là **một cặp**:

- **Request (yêu cầu)**: client gửi đi — "Tôi muốn *cái này*, đây là thông tin kèm theo."
- **Response (phản hồi)**: server trả về — "Kết quả là *thế này*, đây là dữ liệu."

```
Client ──── Request ────► Server
Client ◄─── Response ──── Server
```

Quy tắc: **1 request → đúng 1 response**. Không có response nào mà không có request trước nó.

### 1.4. Ví dụ đời thường

Nhà hàng:
- Bạn (client) gọi món: "Cho 1 phở bò tái, không hành" → **request** (món = cái muốn lấy, "không hành" = thông tin kèm theo).
- Bếp (server) làm xong, mang ra: tô phở → **response**. Hoặc: "Hết bò rồi anh ơi" → vẫn là response, chỉ là kết quả lỗi.
- Bếp không tự mang món ra khi bạn chưa gọi.

### 1.5. Một trang web = rất nhiều request

Mở một trang báo, trình duyệt thường gửi **hàng chục đến hàng trăm** request: 1 cho HTML, vài cái cho CSS, JS, hàng chục cái cho ảnh, font, rồi các request API lấy dữ liệu.

👉 **Tự thử ngay**: mở Chrome → F12 → tab **Network** → F5 lại trang bất kỳ. Mỗi dòng bạn thấy là **một cặp request–response**. Click vào một dòng để xem Headers, Response. Đây là thói quen quan trọng nhất của lập trình viên web.

### 1.6. Tính "stateless" (không trạng thái) — rất quan trọng

HTTP được thiết kế để **mỗi request độc lập**: server **không tự nhớ** request trước của bạn. Request thứ 2 đến, với server nó như người lạ hoàn toàn.

→ Vậy làm sao web biết bạn đã đăng nhập? Đó chính là lý do tồn tại của **Cookie / Session / Token** (phần 6). Ghi nhớ câu hỏi này.

## 2. URL gồm những phần nào

### 2.1. URL là gì

**URL (Uniform Resource Locator)** = "địa chỉ" của một tài nguyên trên mạng. Nó trả lời đồng thời các câu hỏi: **dùng giao thức gì**, **đến máy nào**, **cửa nào**, **lấy cái gì**, **với điều kiện gì**, **nhảy tới đoạn nào**.

### 2.2. Giải phẫu một URL đầy đủ

```
 https://api.example.com:8443/products/42/reviews?sort=new&page=2#comment-7
 └─┬─┘   └──────┬──────┘ └┬─┘└─────────┬────────┘ └──────┬──────┘ └───┬────┘
 scheme      domain      port        path              query       fragment
```

| Phần | Ví dụ | Ý nghĩa | Ai dùng nó |
|---|---|---|---|
| **scheme** | `https` | Giao thức để nói chuyện | Trình duyệt |
| **domain** (host) | `api.example.com` | Máy chủ nào | DNS → ra IP |
| **port** | `8443` | Cửa nào trên máy đó | Hệ điều hành của server |
| **path** | `/products/42/reviews` | Tài nguyên nào | Server (router) |
| **query** | `sort=new&page=2` | Tham số bổ sung | Server |
| **fragment** | `comment-7` | Vị trí trong trang | **Chỉ trình duyệt** — không gửi lên server |

### 2.3. Từng phần, đi vào bản chất

#### a) Scheme — "nói chuyện bằng ngôn ngữ gì"

- `http` — HTTP không mã hóa.
- `https` — HTTP chạy bên trong một đường ống mã hóa TLS.
- Các scheme khác: `ftp://`, `mailto:abc@x.com`, `file:///C:/a.txt`, `ws://` / `wss://` (WebSocket), `jdbc:mysql://...` (bạn đã gặp trong Spring Boot — cùng ý tưởng!).

Scheme còn quyết định **port mặc định**: `http` → 80, `https` → 443.

#### b) Domain — "máy nào"

- Là **tên dễ nhớ** thay cho địa chỉ IP. Chi tiết ở phần 3.
- Có thể là IP trực tiếp: `http://192.168.1.10:3000`.
- `localhost` là một tên đặc biệt = "chính máy này" (thường là `127.0.0.1`).

#### c) Port — "cửa nào"

Hình dung: **IP là địa chỉ tòa nhà**, **port là số phòng**. Một máy có 65.535 port, mỗi chương trình server "ngồi nghe" (listen) ở một port.

| Port | Thường dùng cho |
|---|---|
| 80 | HTTP |
| 443 | HTTPS |
| 22 | SSH |
| 3306 | MySQL |
| 5432 | PostgreSQL |
| 3000, 5173, 8080 | Server dev (Node, Vite, Spring Boot...) |

Vì sao `https://google.com` không ghi port? Vì trình duyệt **tự hiểu** là 443. Ghi `https://google.com:443` cũng y như vậy.

Lỗi quen thuộc `Port 8080 already in use` = đã có chương trình khác ngồi ở phòng 8080 rồi.

#### d) Path — "lấy cái gì"

- Ngày xưa path **khớp với đường dẫn thư mục thật** trên server: `/images/logo.png` → file `/var/www/images/logo.png`.
- Ngày nay path thường chỉ là **chuỗi định danh** để code backend (router) quyết định chạy hàm nào:
  ```java
  @GetMapping("/products/{id}")   // Spring Boot
  public Product get(@PathVariable Long id) { ... }
  ```
  Không có thư mục `products/42` nào cả — `42` được bóc ra làm tham số.
- Phân biệt hoa/thường: tùy server, nhưng nên coi là **có phân biệt**.

#### e) Query — "với điều kiện gì"

- Bắt đầu sau dấu `?`, gồm các cặp `key=value` nối bằng `&`.
- Dùng cho: lọc, sắp xếp, phân trang, tìm kiếm — những thứ **tùy chọn**, **không định danh** tài nguyên.
  - `/products?category=phone&sort=price_asc&page=3`
- **Path vs Query — khi nào dùng cái nào?**
  - Path: xác định **cái gì** (`/products/42` = sản phẩm số 42).
  - Query: xác định **lọc/hiển thị thế nào** (`/products?color=red`).
- **URL encoding**: URL chỉ cho phép một số ký tự. Dấu cách, tiếng Việt, `&`, `=`... phải mã hóa:
  - `tai nghe` → `tai%20nghe` hoặc `tai+nghe` (trong query)
  - `áo` → `%C3%A1o` (byte UTF-8 dạng hex)
  - Nếu tên sản phẩm chứa `&` mà không mã hóa → server tưởng là bắt đầu tham số mới → bug.
- ⚠️ Query **hiện trên thanh địa chỉ, lưu trong lịch sử, log server** → **không bao giờ** đặt mật khẩu, token vào query.

#### f) Fragment — "nhảy tới đâu trong trang"

- Sau dấu `#`.
- **Không được gửi lên server.** Trình duyệt giữ lại cho riêng mình. Mở F12 → Network sẽ thấy request không có `#...`.
- Dùng để cuộn tới phần tử có `id` tương ứng (`<div id="comment-7">`) — chính các link trong mục lục file này dùng fragment.
- Các SPA đời cũ (Angular 1, React HashRouter) dùng fragment để chuyển trang mà không gọi server: `example.com/#/profile`.

### 2.4. Phần ít gặp

URL đầy đủ theo chuẩn còn có `user:password@` trước domain (`ftp://user:pass@host`) — hầu như không dùng trên web nữa vì không an toàn.

### 2.5. URL tuyệt đối vs tương đối

- Tuyệt đối: `https://site.com/img/a.png`
- Tương đối: `/img/a.png` (so với domain hiện tại), `../a.png` (so với thư mục hiện tại). Trình duyệt tự ghép với URL trang đang mở.

## 3. DNS, IP, Domain, Hosting

### 3.1. IP — địa chỉ thật trên mạng

Mỗi thiết bị tham gia mạng Internet cần một **địa chỉ IP** để các gói tin biết đường đi tới, giống số nhà để bưu tá giao thư.

- **IPv4**: 4 số 0–255, ví dụ `142.250.199.78`. Tổng ~4,3 tỷ địa chỉ → **đã cạn**.
- **IPv6**: dài hơn nhiều, ví dụ `2404:6800:4005:80f::200e`. Số lượng gần như vô hạn.

**IP công khai (public) vs IP riêng (private):**
- Mạng nhà bạn: router được nhà mạng cấp **1 IP public**. Điện thoại, laptop trong nhà nhận **IP private** do router cấp: `192.168.x.x`, `10.x.x.x`, `172.16–31.x.x`.
- Router làm **NAT**: dịch qua lại giữa IP private và IP public. Vì vậy cả nhà ra Internet bằng chung một IP.
- Hệ quả: chạy server trên laptop ở `192.168.1.5:8080` → bạn cùng phòng (cùng Wi-Fi) truy cập được, người ở nhà khác **không** truy cập được. Muốn ra Internet phải deploy lên hosting hoặc dùng tool như ngrok / Cloudflare Tunnel.

`127.0.0.1` (localhost): địa chỉ "vòng lặp", gói tin không rời khỏi máy.

### 3.2. Domain — tên dễ nhớ

Không ai nhớ được `142.250.199.78`, nên ta dùng **tên miền**: `google.com`.

Cấu trúc đọc **từ phải sang trái**, từ cấp cao xuống thấp:

```
    mail . google . com .
     │       │       │   └── root (gốc, thường bị ẩn)
     │       │       └────── TLD (top-level domain): com, vn, org, edu.vn...
     │       └────────────── second-level domain: tên bạn mua
     └────────────────────── subdomain: bạn tự tạo thoải mái
```

- `haui.edu.vn`: `vn` là TLD, `edu.vn` là vùng dành cho giáo dục, `haui` là tên trường đăng ký.
- Bạn **mua (thuê theo năm)** domain từ nhà đăng ký (registrar) như Mắt Bão, PA Vietnam, Namecheap, Cloudflare...
- Khi đã sở hữu `myshop.vn`, bạn tự tạo bao nhiêu subdomain cũng được: `api.myshop.vn`, `admin.myshop.vn`... không mất tiền thêm.

**Tại sao không dùng thẳng IP?** Ngoài lý do dễ nhớ:
- IP của server có thể **đổi** (chuyển nhà cung cấp, thêm server) — domain giữ nguyên, chỉ cần sửa bản ghi DNS.
- Một domain có thể trỏ tới **nhiều IP** (chia tải, phục vụ theo vùng địa lý).
- Một IP có thể chứa **nhiều website** (shared hosting) — server phân biệt nhờ header `Host` trong request.

### 3.3. DNS — "danh bạ điện thoại" của Internet

**DNS (Domain Name System)** chuyển **domain → IP**. Nó là một hệ thống **phân tán, phân cấp** khổng lồ, không phải một máy duy nhất.

#### Quá trình tra cứu `www.example.com`

```
Trình duyệt: "www.example.com là IP gì?"
   │
   ├─ 1. Cache của trình duyệt có không? → có thì xong
   ├─ 2. Cache của hệ điều hành / file hosts có không?
   ├─ 3. Hỏi DNS Resolver (của nhà mạng, hoặc 8.8.8.8 Google, 1.1.1.1 Cloudflare)
   │       Resolver có cache thì trả luôn. Không có thì nó đi hỏi giùm:
   │       ├─ a. Hỏi Root server:   "ai quản .com?"         → "hỏi máy chủ TLD .com ở đây"
   │       ├─ b. Hỏi TLD server .com: "ai quản example.com?" → "hỏi nameserver ns1.example-dns.com"
   │       └─ c. Hỏi Authoritative nameserver của example.com:
   │                                  "www.example.com?"     → "93.184.215.14"
   └─ 4. Resolver trả IP cho máy bạn và cache lại một thời gian (TTL)
```

- **TTL (Time To Live)**: kết quả được cache bao lâu (ví dụ 300 giây). Đây là lý do khi bạn đổi IP cho domain, có người thấy ngay, có người phải chờ — gọi là "DNS propagation".
- **File hosts** (`C:\Windows\System32\drivers\etc\hosts` hoặc `/etc/hosts`): bạn tự ghi `127.0.0.1 myshop.local` là trình duyệt tin luôn, không hỏi DNS. Hay dùng khi dev.

#### Các loại bản ghi DNS hay gặp

| Bản ghi | Ý nghĩa | Ví dụ |
|---|---|---|
| **A** | domain → IPv4 | `myshop.vn → 103.1.2.3` |
| **AAAA** | domain → IPv6 | |
| **CNAME** | domain → tên khác (bí danh) | `www.myshop.vn → myshop.vn` hoặc `→ myshop.vercel.app` |
| **MX** | máy chủ nhận email của domain | |
| **TXT** | văn bản tùy ý, dùng để xác minh sở hữu, chống giả mạo email | |
| **NS** | nameserver nào quản lý domain này | |

👉 **Tự thử**: mở terminal
```bash
nslookup google.com
# hoặc (Linux/Mac)
dig google.com
```

### 3.4. Hosting — nơi code của bạn "sống"

Website là một chương trình (hoặc một đống file) phải chạy trên **một máy tính bật 24/7, có IP public, mạng ổn định**. **Hosting** là dịch vụ cho thuê chỗ như vậy.

Các mức, từ "ít phải lo" đến "tự lo hết":

| Loại | Bạn nhận được | Phù hợp | Ví dụ |
|---|---|---|---|
| **Static hosting** | Chỗ đặt file HTML/CSS/JS, không chạy code backend | Trang tĩnh, frontend React/Vue đã build | GitHub Pages, Netlify, Vercel, Cloudflare Pages |
| **Shared hosting** | Một góc nhỏ trên server chung với nhiều web khác, thường có cPanel, PHP, MySQL | Web WordPress nhỏ | Các nhà cung cấp hosting VN |
| **PaaS** | Đưa code lên, nền tảng tự build và chạy | Backend Node/Java/Python, không muốn quản server | Render, Railway, Heroku, Fly.io |
| **VPS** | Một máy ảo riêng, có quyền root, tự cài mọi thứ | Muốn tự do, học DevOps, chạy Docker | DigitalOcean, Vultr, VPS Việt Nam |
| **Cloud (IaaS)** | Hàng trăm dịch vụ: máy ảo, database, lưu file, K8s... | Hệ thống lớn | AWS, Google Cloud, Azure |

**Kết nối các mảnh:** Bạn mua domain `myshop.vn` (registrar) → thuê VPS có IP `103.1.2.3` (hosting) → vào trang quản lý DNS tạo bản ghi `A: myshop.vn → 103.1.2.3` → trên VPS chạy Spring Boot cổng 8080, đặt Nginx nghe cổng 80/443 chuyển tiếp vào 8080 → người dùng gõ `myshop.vn` là vào được.

**Domain và hosting là hai thứ riêng biệt.** Có thể mua domain ở chỗ A, hosting ở chỗ B, chỉ cần DNS trỏ đúng.

**CDN (Content Delivery Network)** — biết thêm: mạng lưới server đặt khắp thế giới, giữ bản sao file tĩnh (ảnh, JS, CSS) gần người dùng để tải nhanh. Cloudflare, CloudFront...

## 4. HTTP: method, header, body, status code

### 4.1. HTTP là gì, bản chất

**HTTP (HyperText Transfer Protocol)** là **một bộ quy ước về định dạng tin nhắn** giữa client và server. Nó chỉ quy định: tin nhắn trông như thế nào, có những phần gì, ý nghĩa ra sao.

Điểm bất ngờ với nhiều người: **HTTP/1.1 chỉ là văn bản thuần (text)**. Bạn hoàn toàn có thể gõ tay một request:

```bash
# Kết nối TCP thô tới port 80 rồi gõ tay:
telnet example.com 80
GET / HTTP/1.1
Host: example.com
                       ← (dòng trống, nhấn Enter 2 lần)
```

Server sẽ trả về một đoạn text bắt đầu bằng `HTTP/1.1 200 OK`. Trình duyệt, Postman, axios, fetch... chỉ là công cụ **soạn và đọc** những đoạn text này cho bạn.

(HTTP/2 và HTTP/3 chuyển sang dạng nhị phân, nén và nhanh hơn, nhưng **ý nghĩa** — method, header, body, status — giữ nguyên. Học HTTP/1.1 là hiểu được tất cả.)

### 4.2. Cấu trúc một Request

```http
POST /api/products HTTP/1.1                ← (1) Request line: METHOD  PATH  VERSION
Host: myshop.vn                            ┐
Content-Type: application/json             │
Authorization: Bearer eyJhbGciOi...        │ (2) Headers: các dòng "Tên: Giá trị"
Accept: application/json                   │
Content-Length: 52                         ┘
                                           ← (3) Dòng trống: báo hết header
{"name": "Tai nghe Sony", "price": 1990000}  ← (4) Body (không bắt buộc)
```

### 4.3. Cấu trúc một Response

```http
HTTP/1.1 201 Created                       ← (1) Status line: VERSION  CODE  REASON
Content-Type: application/json             ┐
Location: /api/products/43                 │ (2) Headers
Date: Fri, 20 Nov 2026 13:15:00 GMT        ┘
                                           ← (3) Dòng trống
{"id": 43, "name": "Tai nghe Sony", "price": 1990000}  ← (4) Body
```

So sánh với nhà hàng:
- **Method** = động từ: "gọi món", "đổi món", "hủy món".
- **Path** = món nào.
- **Header** = ghi chú trên phiếu: số bàn, khách VIP, dị ứng gì.
- **Body** = nội dung chi tiết đi kèm.
- **Status code** = bếp trả lời: "xong rồi", "hết món", "anh chưa đặt bàn".

---

### 4.4. Method — "muốn làm gì"

Method nói lên **ý định** của request với tài nguyên ở path.

| Method | Ý định | Có body? | Ví dụ |
|---|---|---|---|
| **GET** | Lấy / đọc | Không (về nguyên tắc) | `GET /products/42` |
| **POST** | Tạo mới / gửi dữ liệu để xử lý | Có | `POST /products` kèm dữ liệu sản phẩm |
| **PUT** | **Thay thế toàn bộ** tài nguyên | Có | `PUT /products/42` kèm **đầy đủ** mọi trường |
| **PATCH** | **Sửa một phần** | Có | `PATCH /products/42` kèm `{"price": 1500000}` |
| **DELETE** | Xóa | Thường không | `DELETE /products/42` |

Ít gặp hơn: `HEAD` (như GET nhưng chỉ lấy header), `OPTIONS` (hỏi server cho phép gì — trình duyệt tự gửi khi kiểm tra CORS).

#### PUT vs PATCH — hay bị hỏi phỏng vấn

Sản phẩm 42 hiện tại: `{"name": "Tai nghe", "price": 2000000, "stock": 10}`

- `PATCH /products/42` với `{"price": 1500000}` → kết quả: `{"name": "Tai nghe", "price": 1500000, "stock": 10}`. Chỉ đổi giá.
- `PUT /products/42` với `{"price": 1500000}` → **theo đúng ngữ nghĩa**, đây là "thay toàn bộ bằng cái này" → `name` và `stock` có thể bị mất / thành null.

(Thực tế nhiều backend làm PUT như PATCH — nhưng bạn cần biết ngữ nghĩa chuẩn.)

#### Hai tính chất quan trọng: Safe và Idempotent

- **Safe (an toàn)**: không làm thay đổi dữ liệu trên server. → **GET, HEAD, OPTIONS**.
  - Hệ quả: trình duyệt, crawler của Google có thể tự gọi GET thoải mái. **Không bao giờ** làm API kiểu `GET /delete-user?id=5` — bot quét link một vòng là mất dữ liệu.
- **Idempotent (lũy đẳng)**: gọi 1 lần hay 10 lần, **trạng thái cuối trên server như nhau**.
  - GET, PUT, DELETE: idempotent. `DELETE /products/42` lần 1 xóa, lần 2 thì sản phẩm đã không còn — trạng thái vẫn là "không có 42".
  - **POST: không idempotent.** Gửi `POST /orders` 2 lần = 2 đơn hàng.
  - Hệ quả thực tế: mạng chập chờn, client không biết request đã tới chưa → với PUT/DELETE gửi lại thoải mái; với POST thì nguy hiểm (thanh toán 2 lần!). Đó là lý do trình duyệt hỏi "Xác nhận gửi lại biểu mẫu?" khi bạn F5 sau khi submit form, và các API thanh toán dùng "idempotency key".
  - PATCH: tùy cách viết (`{"price": 100}` thì idempotent, `{"stock": "+1"}` thì không).

#### GET có body được không? Gửi dữ liệu GET thế nào?

GET gửi tham số qua **query** (`?keyword=abc`). Chuẩn không cấm body trong GET nhưng nhiều server/proxy bỏ qua nó → đừng dùng.

---

### 4.5. Header — "siêu dữ liệu" (metadata)

Header là các cặp `Tên: Giá trị`, mô tả **về** request/response chứ không phải nội dung chính. Tên header không phân biệt hoa thường.

#### Header thường gặp trong Request

| Header | Ý nghĩa | Ví dụ |
|---|---|---|
| `Host` | Domain muốn truy cập (bắt buộc ở HTTP/1.1) — giúp 1 IP chứa nhiều web | `Host: myshop.vn` |
| `User-Agent` | Client là gì | `Mozilla/5.0 (Windows NT 10.0...) Chrome/...` |
| `Accept` | Tôi muốn nhận định dạng gì | `Accept: application/json` |
| `Content-Type` | Body tôi gửi có định dạng gì | `application/json`, `multipart/form-data` |
| `Content-Length` | Body dài bao nhiêu byte | |
| `Authorization` | Thông tin xác thực | `Authorization: Bearer <token>` |
| `Cookie` | Gửi cookie đã lưu | `Cookie: sessionId=abc123` |
| `Origin` / `Referer` | Request đến từ trang nào | |
| `Accept-Language` | Ngôn ngữ ưa thích | `vi-VN,vi;q=0.9,en;q=0.8` |

#### Header thường gặp trong Response

| Header | Ý nghĩa |
|---|---|
| `Content-Type` | Body trả về là gì: `text/html; charset=utf-8`, `application/json`, `image/png` |
| `Set-Cookie` | Bảo trình duyệt lưu cookie |
| `Location` | Dùng với 3xx (chuyển hướng tới đâu) hoặc 201 (tài nguyên mới tạo ở đâu) |
| `Cache-Control` | Được cache bao lâu: `max-age=3600`, `no-store` |
| `Access-Control-Allow-Origin` | CORS — cho phép trang web domain khác gọi API này không |

#### Content-Type quan trọng thế nào?

Body chỉ là một dãy byte. **Content-Type là cách bên nhận biết phải đọc dãy byte đó như thế nào.**
- Gửi JSON mà quên `Content-Type: application/json` → Spring Boot báo lỗi `415 Unsupported Media Type`, Express không parse được `req.body`.
- Server trả ảnh mà khai `text/plain` → trình duyệt hiện ra rác.

Các Content-Type cho body request:
- `application/json` — API hiện đại.
- `application/x-www-form-urlencoded` — form HTML mặc định: body trông như `name=Sony&price=1990000`.
- `multipart/form-data` — form có **upload file**.

---

### 4.6. Body — nội dung chính

- **Request body**: dữ liệu bạn gửi lên (thông tin đăng ký, sản phẩm mới, file ảnh...). Thường đi với POST, PUT, PATCH.
- **Response body**: dữ liệu server trả về (HTML của trang, JSON danh sách sản phẩm, file ảnh...).
- Body có thể rỗng: ví dụ response `204 No Content` sau khi xóa thành công.

Một điểm bản chất: **HTTP không quan tâm body chứa gì** — HTML, JSON, ảnh, video, PDF... đều chỉ là byte. Content-Type mới là thứ cho biết ý nghĩa.

---

### 4.7. Status code — "kết quả thế nào"

Mã 3 chữ số. **Chữ số đầu tiên cho biết nhóm**, chỉ cần nhìn số đầu là biết đại khái chuyện gì xảy ra.

| Nhóm | Ý nghĩa | Lỗi của ai |
|---|---|---|
| **1xx** | Thông tin tạm, đang xử lý (hiếm gặp) | — |
| **2xx** | ✅ Thành công | — |
| **3xx** | ↪️ Chuyển hướng, đi chỗ khác mà lấy | — |
| **4xx** | ❌ **Client** sai | Bên gửi request |
| **5xx** | 💥 **Server** hỏng | Bên server |

#### 2xx — Thành công

| Code | Khi nào |
|---|---|
| **200 OK** | Thành công chung, có body trả về |
| **201 Created** | Tạo mới thành công (sau POST), thường kèm header `Location` |
| **204 No Content** | Thành công nhưng không có gì trả về (hay dùng sau DELETE) |

#### 3xx — Chuyển hướng

| Code | Khi nào |
|---|---|
| **301 Moved Permanently** | Chuyển vĩnh viễn (đổi domain, http → https). Trình duyệt và Google nhớ luôn. |
| **302 Found** / **307** | Chuyển tạm thời (ví dụ: chưa đăng nhập → đẩy về `/login`) |
| **304 Not Modified** | "File bạn đang cache vẫn còn mới, dùng tiếp đi" — tiết kiệm băng thông |

Cơ chế: server trả 3xx + header `Location: <url mới>`, trình duyệt **tự động** gửi request mới tới URL đó.

#### 4xx — Lỗi phía client

| Code | Khi nào | Ví dụ |
|---|---|---|
| **400 Bad Request** | Request sai định dạng / dữ liệu không hợp lệ | JSON sai cú pháp, thiếu trường bắt buộc, giá âm |
| **401 Unauthorized** | **Chưa xác thực** — "Bạn là ai?" | Không gửi token, token hết hạn |
| **403 Forbidden** | **Đã biết bạn là ai, nhưng không có quyền** | User thường gọi API của admin |
| **404 Not Found** | Không tìm thấy tài nguyên | Sai path, sản phẩm id 9999 không tồn tại |
| **405 Method Not Allowed** | Path đúng nhưng method không hỗ trợ | Gọi `DELETE` vào endpoint chỉ cho `GET` |
| **409 Conflict** | Xung đột trạng thái | Đăng ký email đã tồn tại |
| **415 Unsupported Media Type** | Content-Type không hỗ trợ | Quên header `Content-Type: application/json` |
| **422 Unprocessable Entity** | Cú pháp đúng nhưng dữ liệu vô nghĩa (một số API dùng thay 400) | |
| **429 Too Many Requests** | Gọi quá nhiều, bị giới hạn (rate limit) | |

**401 vs 403** — câu hỏi kinh điển:
- 401: bảo vệ hỏi "Anh là ai?", bạn chưa đưa thẻ → **xác thực (authentication)**.
- 403: bạn đưa thẻ nhân viên rồi, nhưng thẻ của bạn không vào được phòng giám đốc → **phân quyền (authorization)**.
(Cái tên "Unauthorized" của 401 là đặt tên sai lịch sử — thực chất nghĩa là "Unauthenticated".)

#### 5xx — Lỗi phía server

| Code | Khi nào |
|---|---|
| **500 Internal Server Error** | Code backend bị lỗi không xử lý (NullPointerException, lỗi SQL...) |
| **502 Bad Gateway** | Server trung gian (Nginx) gọi vào backend nhưng backend trả rác / chết |
| **503 Service Unavailable** | Server quá tải hoặc đang bảo trì |
| **504 Gateway Timeout** | Server trung gian chờ backend quá lâu không thấy trả lời |

**Kinh nghiệm debug:**
- Thấy **4xx** → kiểm tra lại request của mình (URL, method, header, body, token).
- Thấy **5xx** → đi xem **log của server**. Client làm gì cũng vô ích.
- Thấy **502** khi deploy → thường là app backend chưa chạy hoặc chạy sai port so với cấu hình Nginx.

Lưu ý: status code là **quy ước** — backend viết code nào thì trả code đó. API viết tốt dùng code đúng nghĩa. API viết ẩu trả `200 OK` kèm body `{"error": "not found"}` → gây khó cho client. Hãy là người viết API tốt.

## 5. HTTPS, TLS là gì

### 5.1. Vấn đề của HTTP thường

Request của bạn từ laptop tới server đi qua **rất nhiều máy trung gian**: router Wi-Fi quán cà phê, nhà mạng, các router trên đường truyền quốc tế... HTTP gửi **văn bản thuần**, nên bất kỳ ai ở giữa đều có thể:

1. **Đọc trộm** (eavesdropping): thấy mật khẩu, cookie, tin nhắn. Ngồi cùng Wi-Fi công cộng là có thể "nghe lén".
2. **Sửa nội dung** (tampering): chèn quảng cáo, mã độc vào trang bạn nhận. (Từng có nhà mạng chèn quảng cáo vào trang HTTP.)
3. **Giả mạo** (impersonation): dựng server giả, bạn tưởng đang nói chuyện với ngân hàng thật.

### 5.2. HTTPS = HTTP + TLS

- **TLS (Transport Layer Security)** — tiền thân là SSL, nên người ta vẫn quen gọi "chứng chỉ SSL" — là một lớp nằm **giữa** HTTP và đường truyền TCP, tạo ra một **đường ống mã hóa**.
- **HTTPS** chẳng có gì mới về mặt HTTP: vẫn method, header, body, status y nguyên — chỉ là tất cả được **bỏ vào đường ống TLS** trước khi gửi đi.

```
HTTP:   [ HTTP ] ──────────────────► TCP ──► mạng   (ai cũng đọc được)
HTTPS:  [ HTTP ] ──► [ TLS mã hóa ] ──► TCP ──► mạng   (người ở giữa chỉ thấy byte vô nghĩa)
```

TLS đảm bảo **3 điều**, tương ứng 3 vấn đề trên:

| Đảm bảo | Giải quyết | Bằng cách |
|---|---|---|
| **Bảo mật (Confidentiality)** | Đọc trộm | Mã hóa nội dung |
| **Toàn vẹn (Integrity)** | Sửa nội dung | Mã xác thực — sửa 1 bit là bị phát hiện |
| **Xác thực (Authentication)** | Giả mạo | Chứng chỉ số (certificate) |

### 5.3. Hai loại mã hóa (mức khái niệm)

**Mã hóa đối xứng (symmetric)**: cùng 1 chìa khóa để khóa và mở. Ví dụ AES.
- ✅ Rất nhanh.
- ❌ Vấn đề: làm sao gửi chìa khóa cho bên kia mà không bị lộ? Gửi qua mạng thì người ở giữa lấy được luôn.

**Mã hóa bất đối xứng (asymmetric)**: một **cặp khóa** — **public key** (công khai, ai cũng có) và **private key** (bí mật, chỉ chủ sở hữu giữ).
- Thứ khóa bằng public key → chỉ private key mở được.
- Hình dung: **public key là cái ổ khóa mở sẵn** — bạn phát cho cả thế giới. Ai cũng có thể bấm khóa một cái hộp lại, nhưng chỉ bạn có chìa mở.
- ✅ Giải quyết vấn đề trao chìa.
- ❌ Chậm hơn nhiều.

**TLS kết hợp cả hai:** dùng kỹ thuật bất đối xứng (và trao đổi khóa kiểu Diffie–Hellman) **chỉ ở đầu** để hai bên thống nhất được một **khóa phiên đối xứng** bí mật, sau đó dùng khóa đối xứng đó mã hóa toàn bộ dữ liệu cho nhanh.

### 5.4. Chứng chỉ (Certificate) và CA — giải quyết "đúng là bạn không?"

Mã hóa thôi chưa đủ: nếu kẻ gian đứng giữa và đưa **public key của hắn** cho bạn, bạn sẽ mã hóa rất cẩn thận... rồi gửi cho chính kẻ gian.

→ Cần ai đó **bảo lãnh**: "public key này đúng là của `vietcombank.com.vn`."

- **CA (Certificate Authority)**: tổ chức được tin cậy (Let's Encrypt, DigiCert, Sectigo...). Họ kiểm tra bạn có thật sự sở hữu domain, rồi **ký số** lên một tờ "giấy chứng nhận" gồm: domain + public key + thời hạn.
- **Hệ điều hành / trình duyệt** cài sẵn danh sách CA đáng tin. Khi nhận chứng chỉ từ server, trình duyệt kiểm tra:
  1. Chữ ký có đúng của một CA tin cậy không?
  2. Domain trong chứng chỉ có khớp domain đang truy cập không?
  3. Còn hạn không?
- Sai bất kỳ điều gì → màn hình đỏ **"Kết nối của bạn không phải là kết nối riêng tư"** (`NET::ERR_CERT_...`).

Giống **căn cước công dân**: bạn tin tấm thẻ vì có dấu của cơ quan nhà nước (CA), không phải vì người đó tự nói.

👉 **Tự thử**: click biểu tượng ổ khóa/cài đặt cạnh thanh địa chỉ → "Kết nối an toàn" → "Chứng chỉ hợp lệ" → xem ai cấp, cấp cho domain nào, hết hạn bao giờ.

### 5.5. TLS Handshake (bắt tay) — tóm tắt khái niệm

```
Client                                                  Server
  │── "Xin chào, tôi hỗ trợ TLS 1.3, các thuật toán A,B,C" ──►│
  │◄── "Chọn thuật toán B. Đây là CHỨNG CHỈ của tôi" ─────────│
  │   (client kiểm tra chứng chỉ với danh sách CA)           │
  │◄────── hai bên trao đổi thông tin để cùng tính ra ──────►│
  │            một KHÓA PHIÊN đối xứng bí mật                │
  │══════════ Từ đây mọi HTTP request/response ═════════════│
  │══════════ được mã hóa bằng khóa phiên ═════════════════│
```

TLS 1.3 (hiện đại) chỉ cần 1 vòng đi–về để bắt tay xong.

### 5.6. Những hiểu lầm thường gặp

- ❌ "HTTPS = web an toàn, không lừa đảo." → **Sai.** HTTPS chỉ chứng minh bạn đang nói chuyện **đúng với domain đó** qua đường truyền mã hóa. Trang lừa đảo `vietcombank-xacminh.com` cũng có thể có HTTPS hợp lệ (vì nó thật sự sở hữu domain giả đó).
- ❌ "HTTPS giấu hết." → Người ở giữa vẫn biết bạn đang kết nối tới **domain nào / IP nào** và lượng dữ liệu. Họ **không** thấy path, query, header, body, cookie.
- ✅ Ngày nay HTTPS là **bắt buộc**: trình duyệt cảnh báo "Không an toàn" với HTTP, nhiều tính năng (camera, định vị, Service Worker) chỉ chạy trên HTTPS. Chứng chỉ **miễn phí** qua Let's Encrypt; Vercel, Netlify, Cloudflare tự cấp cho bạn.
- `localhost` được trình duyệt coi là an toàn nên dev bằng HTTP vẫn được.

## 6. Cookie, Session, Local Storage

### 6.1. Nhắc lại vấn đề

HTTP là **stateless** (mục 1.6): mỗi request độc lập, server không nhớ bạn. Nhưng:
- Đăng nhập xong, chuyển sang trang khác vẫn phải biết bạn là ai.
- Giỏ hàng phải giữ lại khi bạn lướt tiếp.
- Web nhớ bạn chọn giao diện tối.

→ Cần cơ chế **lưu trạng thái**. Ba khái niệm trong phần này là ba cách khác nhau, ở **những chỗ khác nhau**.

| | Lưu ở đâu | Ai đọc/ghi | Tự gửi lên server? |
|---|---|---|---|
| **Cookie** | Trình duyệt | Server (qua header) và JS (nếu cho phép) | ✅ **Tự động** theo mỗi request |
| **Session** | **Server** | Server | — (chỉ có ID đi qua cookie) |
| **Local Storage** | Trình duyệt | Chỉ JS | ❌ Không |

### 6.2. Cookie

**Cookie** là một mẩu dữ liệu nhỏ (tên = giá trị, tối đa ~4KB) mà **server bảo trình duyệt cất giữ**, và trình duyệt **tự động gửi kèm** trong mọi request sau đó tới cùng domain.

#### Cách hoạt động

```
1. Bạn đăng nhập:
   POST /login   {username, password}               ──►
                                                    ◄──  HTTP/1.1 200 OK
                                                         Set-Cookie: sid=abc123; HttpOnly; Secure; Path=/
   (trình duyệt cất "sid=abc123" vào kho cookie của domain này)

2. Bất kỳ request nào sau đó tới domain này:
   GET /profile
   Cookie: sid=abc123                               ──►   (server đọc cookie → biết là bạn)
```

Bạn **không phải viết code gì** ở client — trình duyệt tự làm. Đây là điểm mấu chốt phân biệt cookie với Local Storage.

Hình dung: **vé gửi xe**. Lần đầu bạn gửi xe, bảo vệ đưa vé (Set-Cookie). Lần sau ra vào, bạn chỉ cần đưa vé (Cookie) là bảo vệ biết xe nào của bạn.

#### Các thuộc tính quan trọng của cookie

| Thuộc tính | Ý nghĩa |
|---|---|
| `Expires` / `Max-Age` | Khi nào hết hạn. **Không có** → cookie phiên, mất khi đóng trình duyệt. |
| `Domain`, `Path` | Gửi cookie cho domain/path nào |
| `HttpOnly` | **JavaScript không đọc được** (`document.cookie` không thấy). Chống bị mã độc XSS lấy trộm. → Cookie đăng nhập **luôn nên** có. |
| `Secure` | Chỉ gửi qua HTTPS |
| `SameSite` | `Strict` / `Lax` / `None` — có gửi cookie khi request xuất phát từ **trang web khác** không. Chống tấn công **CSRF** (trang độc hại lén gửi request tới ngân hàng của bạn, trình duyệt tự đính cookie). |

Mục đích dùng cookie: duy trì đăng nhập, ghi nhớ tùy chọn, theo dõi/quảng cáo (cookie bên thứ ba — đang bị trình duyệt hạn chế dần, và là lý do có các banner "Chấp nhận cookie").

👉 **Tự thử**: F12 → tab **Application** → **Cookies** → xem cookie của trang đang mở, để ý cột HttpOnly, Secure, SameSite.

### 6.3. Session

**Session** là dữ liệu trạng thái của người dùng được **lưu trên server**. Client chỉ giữ một **mã định danh (session ID)** — thường nằm trong cookie.

```
       Trình duyệt                                Server
  ┌─────────────────────┐                ┌──────────────────────────────────┐
  │ Cookie: sid=abc123  │ ── request ──► │ Kho session (RAM / Redis / DB):  │
  └─────────────────────┘                │   abc123 → { userId: 7,          │
                                         │              role: "admin",      │
                                         │              cart: [12, 45] }    │
                                         │   xyz789 → { userId: 9, ... }    │
                                         └──────────────────────────────────┘
```

Quy trình:
1. Đăng nhập đúng → server tạo session mới với một ID **ngẫu nhiên, dài, khó đoán**, lưu `{userId: 7}` vào kho.
2. Gửi ID về qua `Set-Cookie: sid=abc123; HttpOnly`.
3. Mỗi request sau: server lấy `sid` từ cookie → tra kho → biết user 7.
4. Đăng xuất: server **xóa** session `abc123` khỏi kho → cookie cũ thành vô dụng.

Ví dụ: **tủ gửi đồ siêu thị**. Đồ (dữ liệu) nằm trong tủ của siêu thị (server). Bạn chỉ cầm chìa có số tủ (session ID).

**Cookie vs Session — chúng không phải hai lựa chọn đối lập!**
- Cookie là **phương tiện vận chuyển / nơi chứa** ở phía trình duyệt.
- Session là **dữ liệu lưu ở server**.
- Cách phổ biến nhất: **session ID nằm trong cookie**. Chúng làm việc cùng nhau.

Ưu – nhược của session:
- ✅ Dữ liệu nhạy cảm không rời khỏi server; người dùng không sửa được. Đăng xuất / khóa tài khoản có hiệu lực ngay.
- ❌ Server phải lưu trữ. Khi có nhiều server chạy song song, phải dùng kho chung (Redis) để server nào cũng tra được.

**Biết thêm — Token (JWT):** cách thay thế là server không lưu gì, mà cấp cho client một **token có chữ ký** chứa thông tin (`{userId: 7, role: "user", exp: ...}`). Client gửi lại token qua header `Authorization: Bearer <token>` (hoặc cookie). Server chỉ cần **kiểm tra chữ ký** là tin. Phổ biến cho REST API và app di động. Nhược: khó thu hồi trước khi hết hạn.

Trong Spring Boot: session có sẵn qua `HttpSession` (cookie tên `JSESSIONID`); JWT thì cấu hình với Spring Security.

### 6.4. Local Storage

**Local Storage** là một kho **key–value** (chỉ lưu chuỗi) nằm trong trình duyệt, **chỉ JavaScript truy cập**, dung lượng khoảng **5–10MB** mỗi origin.

```javascript
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");            // "dark"
localStorage.removeItem("theme");
localStorage.clear();

// Chỉ lưu được chuỗi → object phải chuyển sang JSON
localStorage.setItem("cart", JSON.stringify([{ id: 12, qty: 2 }]));
const cart = JSON.parse(localStorage.getItem("cart"));
```

Đặc điểm:
- **Không tự gửi lên server.** Muốn server biết, JS phải tự lấy ra và gắn vào request.
- **Không hết hạn** — còn mãi đến khi code xóa hoặc người dùng xóa dữ liệu trình duyệt.
- Phân tách theo **origin** (scheme + domain + port): `http://localhost:3000` và `http://localhost:5173` là hai kho khác nhau.
- **Họ hàng:** `sessionStorage` — y hệt nhưng **mất khi đóng tab**, và mỗi tab một kho riêng. (Tên có chữ "session" nhưng **không liên quan** session phía server!)

Phù hợp: tùy chọn giao diện (dark mode, ngôn ngữ), nháp form, giỏ hàng khách vãng lai, cache dữ liệu không nhạy cảm.

⚠️ **Bảo mật**: bất kỳ JS nào chạy trên trang đều đọc được Local Storage. Nếu trang dính lỗ hổng **XSS** (kẻ gian chèn được script), token lưu trong Local Storage sẽ bị lấy trộm ngay. Cookie `HttpOnly` thì script không đọc được. → Với thông tin đăng nhập, ưu tiên **cookie HttpOnly + Secure + SameSite**. (Nhiều dự án học vẫn lưu JWT vào Local Storage cho đơn giản — chấp nhận được khi học, nhưng hãy biết rủi ro.)

### 6.5. Bảng so sánh tổng hợp

| Tiêu chí | Cookie | Session (server) | Local Storage | Session Storage |
|---|---|---|---|---|
| Nơi lưu | Trình duyệt | Server | Trình duyệt | Trình duyệt |
| Dung lượng | ~4KB/cookie | Tùy server | ~5–10MB | ~5MB |
| Tự gửi lên server | ✅ Mỗi request | (ID đi qua cookie) | ❌ | ❌ |
| JS đọc được | ✅ trừ khi `HttpOnly` | ❌ | ✅ | ✅ |
| Thời hạn | Theo `Expires` / hết phiên trình duyệt | Server quyết định | Vĩnh viễn | Đóng tab là mất |
| Dùng cho | Session ID, token, tùy chọn nhỏ | Trạng thái đăng nhập, quyền | Tùy chọn UI, cache | Dữ liệu tạm 1 tab |

## 7. JSON là gì

### 7.1. Vấn đề

Server viết bằng Java, client viết bằng JavaScript, app Android viết bằng Kotlin, script viết bằng Python. Một object `Product` trong Java **không thể** gửi nguyên xi qua mạng cho JS hiểu — mỗi ngôn ngữ lưu object trong bộ nhớ theo cách riêng.

→ Cần một **định dạng văn bản trung gian** mà mọi ngôn ngữ đều đọc/ghi được. JSON là định dạng phổ biến nhất hiện nay cho việc đó.

### 7.2. JSON là gì

**JSON (JavaScript Object Notation)** là định dạng **văn bản** để biểu diễn dữ liệu có cấu trúc. Cú pháp mượn từ cách viết object trong JavaScript, nhưng **độc lập ngôn ngữ**.

```json
{
  "id": 42,
  "name": "Tai nghe Sony WH-1000XM5",
  "price": 7990000,
  "inStock": true,
  "discount": null,
  "tags": ["bluetooth", "chống ồn"],
  "brand": {
    "name": "Sony",
    "country": "Japan"
  },
  "reviews": [
    { "user": "an", "rating": 5 },
    { "user": "binh", "rating": 4 }
  ]
}
```

### 7.3. Chỉ có 6 kiểu dữ liệu

| Kiểu | Ví dụ |
|---|---|
| **string** | `"Xin chào"` — **bắt buộc nháy kép** |
| **number** | `42`, `-3.14`, `1e6` — không phân biệt int/float |
| **boolean** | `true`, `false` |
| **null** | `null` |
| **object** | `{ "key": value, ... }` — tập hợp cặp key–value |
| **array** | `[value, value, ...]` — danh sách có thứ tự |

Object và array lồng nhau tùy ý → biểu diễn được mọi cấu trúc dữ liệu.

**Không có**: kiểu ngày tháng (dùng chuỗi ISO 8601 `"2026-11-20T13:15:00Z"`), `undefined`, hàm, comment.

### 7.4. Các lỗi cú pháp hay gặp (JSON nghiêm khắc hơn object JS)

```javascript
// ❌ JS object hợp lệ nhưng KHÔNG phải JSON hợp lệ:
{
  name: "Sony",           // key thiếu nháy kép
  'price': 100,           // nháy đơn
  tags: ["a", "b",],      // dấu phẩy thừa cuối
  // comment              // không có comment
}

// ✅ JSON hợp lệ:
{
  "name": "Sony",
  "price": 100,
  "tags": ["a", "b"]
}
```

Khi API trả `400 Bad Request` lúc bạn gửi JSON, nghi ngờ đầu tiên là cú pháp JSON. Dán vào jsonlint.com để kiểm tra.

### 7.5. Serialize và Deserialize — bản chất

- **Serialize** (tuần tự hóa): object trong bộ nhớ → chuỗi JSON (để gửi đi / lưu lại).
- **Deserialize**: chuỗi JSON → object trong bộ nhớ.

```javascript
// JavaScript
const s = JSON.stringify({ id: 1, name: "Sony" });  // object → '{"id":1,"name":"Sony"}'
const o = JSON.parse(s);                            // chuỗi → object
```

```java
// Java (Jackson) — Spring Boot làm tự động khi bạn trả về object hoặc dùng @RequestBody
ObjectMapper mapper = new ObjectMapper();
String json = mapper.writeValueAsString(product);          // serialize
Product p = mapper.readValue(json, Product.class);         // deserialize
```

Khi bạn viết `@RestController` trả về một `Product`, Spring âm thầm gọi Jackson serialize nó thành JSON và đặt header `Content-Type: application/json`. Khi bạn viết `@RequestBody Product p`, Spring deserialize body thành object. Hiểu vậy để khi lỗi (ví dụ getter thiếu, vòng lặp quan hệ JPA gây lỗi serialize vô hạn) bạn biết nó xảy ra ở đâu.

### 7.6. So với các định dạng khác

- **XML**: cũ hơn, dài dòng hơn (`<name>Sony</name>`), vẫn gặp ở hệ thống doanh nghiệp, SOAP, file cấu hình Android/Maven.
- **YAML**: dễ đọc cho người, dùng cho file cấu hình (Docker Compose, K8s, GitLab CI, `application.yml`). YAML thực chất là "siêu tập" của JSON.
- **Protobuf**: nhị phân, nhỏ và nhanh, dùng trong gRPC giữa các microservice.

## 8. REST API là gì

### 8.1. API trước

**API (Application Programming Interface)** = **giao diện để chương trình nói chuyện với chương trình**.
- Giao diện web (UI) dành cho **con người**: nút bấm, ô nhập.
- API dành cho **code**: gửi request đúng định dạng → nhận dữ liệu đúng định dạng.

Ví dụ: app thời tiết trên điện thoại không tự đo nhiệt độ — nó gọi API của một dịch vụ thời tiết, nhận về JSON, rồi vẽ lên màn hình.

"API" theo nghĩa rộng còn là các hàm của thư viện (Java Collections API...). Trong web, "API" thường hiểu là **Web API** — gọi qua HTTP.

### 8.2. REST là gì

**REST (REpresentational State Transfer)** là một **phong cách kiến trúc** (không phải thư viện, không phải giao thức) do Roy Fielding đề xuất năm 2000, mô tả cách thiết kế API **tận dụng đúng tinh thần của HTTP**.

Một API theo phong cách này gọi là **RESTful API**.

### 8.3. Ý tưởng cốt lõi: tài nguyên (resource) + động từ HTTP

Tư duy REST: **mọi thứ là tài nguyên (danh từ)**, mỗi tài nguyên có một **URL**, và bạn thao tác lên nó bằng **method HTTP (động từ)**.

**❌ Kiểu không REST** (động từ nằm trong URL):
```
POST /getAllProducts
POST /getProductById?id=42
POST /createProduct
POST /updateProduct
GET  /deleteProduct?id=42        ← còn nguy hiểm (GET mà xóa)
```

**✅ Kiểu RESTful** (URL là danh từ, method là động từ):

| Hành động | Method | URL | Body | Response thành công |
|---|---|---|---|---|
| Lấy danh sách | `GET` | `/products` | — | `200` + mảng JSON |
| Lấy 1 cái | `GET` | `/products/42` | — | `200` + object, hoặc `404` |
| Tạo mới | `POST` | `/products` | JSON sản phẩm | `201` + object mới + `Location` |
| Thay toàn bộ | `PUT` | `/products/42` | JSON đầy đủ | `200` |
| Sửa một phần | `PATCH` | `/products/42` | JSON vài trường | `200` |
| Xóa | `DELETE` | `/products/42` | — | `204` |

Chỉ có **2 URL** (`/products` và `/products/{id}`) mà đủ toàn bộ CRUD. Ai đã quen REST nhìn vào là đoán được ngay API hoạt động thế nào — đó chính là giá trị của nó: **tính nhất quán, dễ đoán**.

### 8.4. Quy ước đặt URL

- Dùng **danh từ số nhiều**: `/products`, `/users`, `/orders`.
- Chữ thường, nối bằng gạch ngang: `/order-items`.
- Quan hệ cha–con lồng nhau: `/users/7/orders` (đơn hàng của user 7), `/products/42/reviews`.
- Lọc, sắp xếp, phân trang dùng **query**: `/products?category=audio&sort=-price&page=2&size=20`.
- Có phiên bản: `/api/v1/products`.
- Hành động không vừa khung CRUD: chấp nhận thực dụng, ví dụ `POST /orders/15/cancel` hoặc mô hình hóa thành tài nguyên `POST /orders/15/cancellation`.

### 8.5. Các nguyên tắc của REST (biết ở mức khái niệm)

1. **Client – Server tách biệt**: frontend và backend phát triển độc lập, chỉ thỏa thuận qua API.
2. **Stateless**: mỗi request phải **tự chứa đủ thông tin** để xử lý (ví dụ kèm token). Server không dựa vào "lần trước client đã nói gì". → Dễ mở rộng: thêm bao nhiêu server cũng được, request nào đến server nào cũng xử lý được.
3. **Cacheable**: response phải cho biết có được cache không (qua header).
4. **Giao diện thống nhất (Uniform Interface)**: tài nguyên định danh bằng URL, thao tác bằng method chuẩn, dùng status code chuẩn.
5. **Layered system**: client không cần biết phía sau có bao nhiêu tầng (load balancer, cache, API gateway...).

Chữ "**Representational State Transfer**" nghĩa là: client không chạm trực tiếp vào tài nguyên trong database, mà nhận/gửi một **bản biểu diễn (representation)** của nó — thường là JSON (cũng có thể XML). Cùng một sản phẩm có thể biểu diễn bằng JSON cho app, bằng HTML cho trình duyệt.

### 8.6. Ví dụ một API viết tốt — phần lỗi

Đừng chỉ trả status code; hãy trả body lỗi có cấu trúc để client hiển thị được:

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "status": 400,
  "error": "Validation failed",
  "details": [
    { "field": "price", "message": "Giá phải lớn hơn 0" },
    { "field": "name",  "message": "Tên không được để trống" }
  ]
}
```

### 8.7. Ví dụ Spring Boot ứng với bảng ở 8.3

```java
@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    @GetMapping                       // GET /api/v1/products?page=0
    public List<Product> list(@RequestParam(defaultValue = "0") int page) { ... }

    @GetMapping("/{id}")              // GET /api/v1/products/42
    public ResponseEntity<Product> get(@PathVariable Long id) {
        return repo.findById(id)
                   .map(ResponseEntity::ok)                  // 200
                   .orElse(ResponseEntity.notFound().build()); // 404
    }

    @PostMapping                      // POST /api/v1/products
    public ResponseEntity<Product> create(@RequestBody Product p) {
        Product saved = repo.save(p);
        return ResponseEntity.created(URI.create("/api/v1/products/" + saved.getId()))
                             .body(saved);                  // 201 + Location
    }

    @DeleteMapping("/{id}")           // DELETE /api/v1/products/42
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        repo.deleteById(id);
        return ResponseEntity.noContent().build();          // 204
    }
}
```

Mọi khái niệm từ đầu tài liệu đều xuất hiện ở đây: path, path variable, query, method, body, JSON, status code, header `Location`.

### 8.8. Các lựa chọn khác ngoài REST (biết tên)

- **GraphQL**: một endpoint duy nhất, client tự mô tả muốn lấy trường nào → tránh lấy thừa/thiếu.
- **gRPC**: nhị phân (Protobuf), nhanh, hay dùng giữa các microservice.
- **WebSocket**: kết nối hai chiều liên tục — chat, game, thông báo thời gian thực.

## 9. Dùng Postman / Bruno / Insomnia

### 9.1. Chúng là gì, để làm gì

Cả ba đều là **API client** — ứng dụng giúp bạn **tự soạn HTTP request bằng giao diện** và **xem response chi tiết**, không cần viết code frontend.

Dùng để:
- **Thử API công khai** để hiểu nó trước khi viết code gọi.
- **Test backend của chính mình** (Spring Boot, Express) ngay khi vừa viết xong endpoint, chưa có frontend.
- **Debug**: frontend báo lỗi → gọi thử bằng Postman → nếu Postman vẫn lỗi thì lỗi ở backend, nếu Postman ổn thì lỗi ở frontend. Khoanh vùng cực nhanh.
- **Lưu bộ sưu tập request** (collection) chia sẻ cho nhóm, dùng biến môi trường (dev/production), viết test tự động.

| Công cụ | Đặc điểm |
|---|---|
| **Postman** | Phổ biến nhất, nhiều tính năng, nhiều tài liệu. Cần tài khoản, dữ liệu đồng bộ lên cloud. |
| **Bruno** | Mã nguồn mở, **offline**, lưu collection thành **file văn bản trong thư mục dự án** → commit vào Git cùng code được. Rất hợp làm bài tập nhóm. |
| **Insomnia** | Giao diện gọn, hỗ trợ tốt REST, GraphQL, gRPC. |

Chọn cái nào cũng được — khái niệm giống nhau 100%. Nếu chưa biết chọn: **Postman** để theo tài liệu dễ, **Bruno** nếu muốn lưu vào Git.

Công cụ dòng lệnh tương đương: **curl** (có sẵn trên hầu hết máy). Postman có nút "Code" để chuyển request thành lệnh curl / code JS / Java.

### 9.2. Giao diện chung (cả 3 đều tương tự)

```
┌──────────────────────────────────────────────────────────────────┐
│ [GET ▼]  https://jsonplaceholder.typicode.com/posts/1   [ Send ] │  ← method + URL
├──────────────────────────────────────────────────────────────────┤
│  Params | Headers | Body | Auth                                  │  ← soạn request
├──────────────────────────────────────────────────────────────────┤
│  Status: 200 OK     Time: 120 ms     Size: 1.2 KB                │  ← kết quả
│  Body | Headers | Cookies                                        │
│  {                                                               │
│    "userId": 1,                                                  │
│    "id": 1,                                                      │
│    "title": "sunt aut facere ...",                               │
│    ...                                                           │
└──────────────────────────────────────────────────────────────────┘
```

- **Params**: điền query dạng bảng, tool tự ghép vào URL và tự URL-encode.
- **Headers**: thêm header.
- **Body**: chọn `raw` → `JSON` để gửi JSON (tool tự thêm `Content-Type: application/json`), hoặc `form-data` để upload file.
- **Auth**: chọn `Bearer Token` → tool tự thêm `Authorization: Bearer ...`.

### 9.3. Bài thực hành với API công khai

**API thực hành 1 — JSONPlaceholder** (`https://jsonplaceholder.typicode.com`): API giả lập blog, đủ đủ CRUD, không cần đăng ký. Lưu ý: POST/PUT/DELETE **trả về như thật nhưng không lưu** dữ liệu.

| # | Làm gì | Quan sát gì |
|---|---|---|
| 1 | `GET /posts` | Status 200, body là **mảng** 100 bài. Xem tab Headers response: `Content-Type: application/json; charset=utf-8`. |
| 2 | `GET /posts/1` | Body là **1 object**. |
| 3 | `GET /posts/9999` | Status **404**. |
| 4 | `GET /posts?userId=2` (điền ở tab Params) | Lọc bằng query. Nhìn URL được ghép tự động. |
| 5 | `GET /users/1/posts` | Tài nguyên lồng nhau kiểu REST. |
| 6 | `POST /posts`, Body → raw → JSON: `{"title": "Bài của tôi", "body": "Nội dung", "userId": 1}` | Status **201 Created**, server trả object kèm `id: 101`. |
| 7 | Lặp lại bước 6 nhưng **xóa header Content-Type** (hoặc chọn Body kiểu Text) | Server không hiểu body → response chỉ có `id`, thiếu dữ liệu. Hiểu vì sao Content-Type quan trọng. |
| 8 | `PUT /posts/1` với `{"title": "Mới"}` | Response **chỉ còn** `title` và `id` → minh họa PUT = thay toàn bộ. |
| 9 | `PATCH /posts/1` với `{"title": "Mới"}` | Response vẫn giữ `body`, `userId` → PATCH = sửa một phần. |
| 10 | `DELETE /posts/1` | Status 200, body `{}`. |

**API thực hành 2 — httpbin** (`https://httpbin.org`): "tấm gương" phản chiếu lại request của bạn — tuyệt vời để **thấy** những gì bạn thực sự gửi đi.

| Request | Học được gì |
|---|---|
| `GET /get?name=An&age=20` | Server trả lại các query `args`, các header bạn gửi (kể cả header Postman tự thêm như `User-Agent`). |
| `POST /post` với body JSON | Xem body bạn gửi được nhận ra sao. |
| `GET /headers` kèm header tự thêm `X-Hello: world` | Header tùy chỉnh đến được server. |
| `GET /status/404`, `/status/500`, `/status/301` | Quan sát từng loại status code. |
| `GET /cookies/set?theme=dark` | Server trả `Set-Cookie` + chuyển hướng 302. Xem tab Cookies của Postman — nó lưu cookie như trình duyệt. Gọi tiếp `GET /cookies` để thấy cookie tự gửi lại. |
| `GET /basic-auth/user/pass` với tab Auth → Basic Auth | Không điền → **401**. Điền `user` / `pass` → 200. |
| `GET /delay/3` | Response chậm 3 giây — xem cột Time. |

**API thực hành 3 — vui hơn, dữ liệu thật:**
- `https://pokeapi.co/api/v2/pokemon/pikachu` — JSON lồng nhiều tầng, luyện đọc cấu trúc JSON.
- `https://api.github.com/users/<tên-github-của-bạn>` — thông tin GitHub công khai. Xem các header `x-ratelimit-remaining` (giới hạn số lần gọi — gọi quá sẽ nhận 403/429).
- `https://open.er-api.com/v6/latest/USD` — tỷ giá tiền tệ.

### 9.4. Một số tính năng nên biết sớm

- **Collection**: gom các request của một dự án thành thư mục, lưu lại, chia sẻ.
- **Environment / biến**: định nghĩa `{{baseUrl}} = http://localhost:8080` cho môi trường dev, `https://api.myshop.vn` cho production. Request viết `{{baseUrl}}/api/products` → đổi môi trường bằng một click.
- **Lưu token tự động**: script sau request login lấy token gán vào biến, các request sau dùng `{{token}}`.
- **Tests**: viết đoạn kiểm tra như "status phải là 200", "body có trường id" → chạy cả collection để kiểm thử hồi quy. (Rất liên quan đến môn Đảm bảo chất lượng phần mềm.)

### 9.5. Tương đương bằng curl (để hiểu tool đang làm gì phía dưới)

```bash
# GET
curl https://jsonplaceholder.typicode.com/posts/1

# Xem cả header response (-i) hoặc toàn bộ quá trình (-v)
curl -i https://jsonplaceholder.typicode.com/posts/1
curl -v https://httpbin.org/get

# POST JSON
curl -X POST https://jsonplaceholder.typicode.com/posts \
     -H "Content-Type: application/json" \
     -d '{"title": "Hello", "body": "World", "userId": 1}'

# Kèm token
curl https://api.example.com/me -H "Authorization: Bearer <token>"
```

Chạy `curl -v` một lần và đọc kỹ output: bạn sẽ thấy **DNS → kết nối IP:443 → TLS handshake → request text → response text** — toàn bộ tài liệu này trong một màn hình.

## 10. Tổng kết & tự kiểm tra

### 10.1. Một câu cho mỗi khái niệm

- **Client – Server**: client chủ động hỏi, server chờ và phục vụ; "server" là vai trò, không phải loại máy.
- **Request – Response**: mỗi lượt giao tiếp là 1 cặp hỏi – đáp; HTTP stateless nên mỗi request độc lập.
- **URL**: `scheme://domain:port/path?query#fragment` — giao thức, máy, cửa, tài nguyên, tham số, vị trí trong trang (fragment không gửi lên server).
- **IP**: địa chỉ thật để định tuyến gói tin. **Domain**: tên dễ nhớ. **DNS**: hệ thống phân tán đổi domain → IP. **Hosting**: máy chạy 24/7 có IP public để chứa ứng dụng.
- **HTTP**: quy ước định dạng tin nhắn gồm method (ý định), header (siêu dữ liệu), body (nội dung), status code (kết quả: 2 ổn, 3 đi chỗ khác, 4 client sai, 5 server hỏng).
- **HTTPS / TLS**: HTTP chạy trong đường ống mã hóa; chống đọc trộm, chống sửa, xác thực server bằng chứng chỉ do CA ký.
- **Cookie**: dữ liệu nhỏ server bảo trình duyệt giữ, tự động gửi lại mỗi request. **Session**: trạng thái lưu ở server, client chỉ giữ ID (thường trong cookie). **Local Storage**: kho key–value trong trình duyệt, chỉ JS dùng, không tự gửi.
- **JSON**: định dạng văn bản trung gian, 6 kiểu dữ liệu, để mọi ngôn ngữ trao đổi dữ liệu.
- **REST API**: phong cách thiết kế API — URL là danh từ (tài nguyên), method HTTP là động từ, dùng status code đúng nghĩa, stateless.
- **Postman / Bruno / Insomnia**: công cụ đóng vai client để soạn request và đọc response — test, debug, khám phá API.

### 10.2. Câu hỏi tự kiểm tra (trả lời được hết là đã hiểu bản chất)

1. Vì sao laptop của bạn chạy Spring Boot cũng có thể gọi là "server"?
2. Trong `https://shop.vn:8443/cart?coupon=SALE#total`, phần nào **không** được gửi lên server? Port thực tế là bao nhiêu? Nếu bỏ `:8443` thì port là bao nhiêu?
3. Vì sao không nên đặt mật khẩu trong query của URL kể cả khi dùng HTTPS?
4. Bạn đổi IP server cho domain, bạn cùng lớp vẫn vào server cũ. Giải thích.
5. Bạn chạy server ở `192.168.1.5:8080`. Vì sao bạn ở nhà khác không truy cập được?
6. `POST /orders` bị timeout, client tự gửi lại. Chuyện gì có thể xảy ra? Nếu là `PUT` thì sao?
7. Phân biệt 401 và 403 bằng một ví dụ của riêng bạn.
8. Frontend gọi API nhận 502. Bạn kiểm tra gì đầu tiên?
9. Trang lừa đảo có ổ khóa HTTPS — điều đó chứng minh gì và không chứng minh gì?
10. Cookie và Session có phải là hai lựa chọn thay thế nhau không? Giải thích cách chúng phối hợp.
11. Vì sao cookie đăng nhập nên có `HttpOnly`? Lưu token ở Local Storage có rủi ro gì?
12. Gửi JSON lên Spring Boot nhận `415`. Nguyên nhân khả dĩ nhất?
13. Viết lại các endpoint `/getUser?id=5`, `/createUser`, `/deleteUser?id=5` theo phong cách REST, kèm status code thành công phù hợp.
14. Dùng Postman gọi `PUT` và `PATCH` lên `jsonplaceholder.typicode.com/posts/1` với cùng body `{"title":"x"}`. Giải thích vì sao kết quả khác nhau.

### 10.3. Gợi ý bước tiếp theo

- Mở **F12 → Network** trên mọi trang bạn dùng hằng ngày, tập đọc từng request: method, status, header, response.
- Viết một REST API nhỏ (Spring Boot hoặc Express) có đủ CRUD, test toàn bộ bằng Postman/Bruno, dùng đúng status code.
- Viết frontend nhỏ dùng `fetch()` gọi API đó, lưu tùy chọn dark mode bằng Local Storage.
- Deploy lên một hosting miễn phí (Render, Railway cho backend; Vercel, Netlify cho frontend) — bạn sẽ chạm vào domain, DNS, HTTPS trong thực tế.
